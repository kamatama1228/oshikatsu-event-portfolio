# 推しイベ! — 推し活イベント情報アプリ(チーム開発)

ライブやイベントの情報がSNSに散らばっていて追いきれない、という課題に対して、**公演単位で情報を1ページに集約する**Webアプリです。3日間のインターンシップのハッカソンで、4人チームで開発しました。

- 期間: 3日間
- 体制: 4人(フロントエンド2名 / バックエンド1名 / 全体1名)
- 自分の役割: **フロントエンド**(イベント詳細・ホーム・イベント追加申請・パスワード管理の各画面)
- チームリポジトリ: https://github.com/jigintern/202609-3days-hackathon-team-a

このREADMEは**自分が担当した範囲**についてまとめたものです。

---

## 企画 — テーマから対象を絞り込むまで

インターンシップのテーマは「推し活」でした。範囲が広いままだと3日で作り切れないため、**まず市場の実態を調べてスコープを狭める**ところから始めました。

その材料として自分が見つけてきたのが、財務省の広報誌『ファイナンス』の次の記事です。

- [『ファイナンス』2025年11月号(財務省)](https://www.mof.go.jp/public_relations/finance/2025011/202511f.pdf)

この記事から、推し活の中でも**アイドル・アーティスト領域の市場が活況である**ことを確認し、ここに対象を絞る判断材料としました。その前提でチーム全員でブレインストーミングを行い、作るものを決めました。

決まった課題と解決の方針は次のとおりです。

| 課題 | 解決策 |
| --- | --- |
| ライブの詳細をSNS頼りで探しており、告知方法も運営ごとにバラバラ | 公演ごとに1ページへ集約し、**公式情報 / ファンの投稿 / その場の会話**を3つのタブに分離 |

## 担当した機能

### イベント詳細画面(このアプリの中心画面)

3つのタブで構成される画面を、タブの骨組みから各タブの中身まで実装しました。

- **公式アカウントタブ**: 運営が入稿した情報を新着順に表示
- **ユーザータブ**: ファンの投稿一覧(いいね数順 / 最新順の切り替え、カーソル方式のページング)、投稿作成、画像添付(最大4枚)、いいね、自分の投稿の削除
- **チャットタブ**: 3秒間隔のポーリングによる差分取得、発言の送信・削除、新着時の自動スクロール

### その他の画面

- **ホーム**: フォロー中アーティストの開催予定イベントを開催日順に表示
- **イベント追加申請**: 未登録のイベントを運営に申請するフォームと、自分の申請の状態表示。アーティストはプルダウンから選択でき、一覧にない場合は自由入力に切り替わる(名前・ふりがなでの絞り込み付き)
- **パスワード管理**: マスターパスワードによるアンロック、認証情報の登録・編集・削除。**暗号化・復号・鍵の管理をすべてブラウザ内で完結**させ、サーバーには暗号文のみを送る

### 環境構築とデザイン適用

- プロジェクト初期のフロントエンド環境構築(Vite / React / React Router / Supabase クライアント)
- チームで導入したデザインシステムに合わせ、担当画面のスタイルを適用

## 技術選定

全体構成は仕様を固める段階でチームとして決めたものです。そのうち**自分が担当したフロントエンドについて、選定の理由**は次のとおりです。

| 選んだもの | 理由 |
| --- | --- |
| **React + Vite** | 画面遷移が多いSPAであること、開発サーバーの起動とビルドが速く、3日間で試行回数を稼げること |
| **React Router** | 仕様が画面をパス単位で定義していたため、そのまま対応付けられる |
| **Supabase Auth** | 認証を自前で実装しない判断。パスワードのハッシュ化・セッション管理・トークン更新を任せられるため、限られた時間を本来の機能に使える |
| **Web Crypto API**(PBKDF2 / AES-GCM) | パスワード管理の暗号化に、**ライブラリを追加せず**標準APIだけで対応できる。3日間の開発で依存を増やすリスクを避けた |

### あえて採用しなかったもの

- **状態管理ライブラリ(Redux など)**: データ取得は画面ごとに完結する形が中心で、共有が必要だったのは認証情報と保管庫の鍵だけでした。React の Context と `useState` で足りるため導入していません
- **UIコンポーネントライブラリ(MUI など)**: 独自のデザインに寄せる前提だったこと、バンドルサイズと学習コストを避けたことから、CSSを自前で書いています

## 設計上の判断

### 投稿に返信機能を付けず、会話はチャットに分離した

投稿へのリプライ機能(ツリー構造)は実装していません。代わりに、

- **投稿** = 残しておきたい情報(「物販は東ゲート、30分待ち」など)。いいね数順に並ぶため、有用な情報が上に来る
- **チャット** = その場の会話。時系列で流れてよい内容

と役割を分けました。返信ツリーを実装せずに会話のニーズを満たせるうえ、投稿一覧が会話で埋もれることも防げます。

### パスワード管理は、サーバーが復号鍵を持たない設計にした

扱うのが実在のチケットサイトの会員番号やパスワードであるため、**サーバーが破られても中身が読めない**構成にしました。

- マスターパスワードから PBKDF2-HMAC-SHA256(60万回)で鍵を導出し、AES-GCM で暗号化してから送信する
- 導出した鍵はメモリ上にのみ保持し、`localStorage` などには保存しない(`extractable: false`)
- マスターパスワードの照合もサーバーではできないため、既知の文字列を復号できるかどうかで判定する

サーバー側で暗号化する方式も検討されましたが、**鍵がデータの隣にあると漏れたときに一緒に漏れる**ため採用していません。一方で、暗号文の保管はサーバーに置いています(端末を変えても使えるようにするため)。

### API のレスポンスに足りない情報を、仕様と照らして特定し依頼した

「自分の投稿は削除できる」という仕様が実装できない状態になっていました。原因は、投稿一覧の API が投稿者を判別する情報を返していないことでした。表示名での比較は同名ユーザーがいると誤判定するため採用せず、**必要なフィールドと理由を添えてバックエンド担当に依頼**し、追加後に削除機能を実装しました。

同様に、連投防止のクールダウン中に残り秒数を表示する仕様も、エラーレスポンスの `retryAfter` をフロントが受け取れない状態だったため、共有ファイルの変更可否をチームに確認したうえで対応しました。

## AI駆動開発について

今回は**AIを全面的に利用して開発**しました。実装そのものはAIに任せ、**自分は判断とレビューを担う**進め方です。

具体的には次のように使い分けました。

- **決めるのは自分**: 何を作らないか(投稿への返信機能を付けない)、どこまで触るか(他の人の担当ファイルや共通ファイルは合意を取ってから)、仕様と実装が食い違ったときにどちらを直すか
- **実装はAI**: 画面の実装、API連携、スタイルの適用
- **レビューもAIに走らせたうえで、採否は自分が判断**: 指摘の中には「実装コストに見合わない」「今のPRの範囲を超える」ものもあるため、その場で直すか、PRの説明に課題として残すかを切り分けた
- **事実確認は必ず自分で**: 不具合の報告を受けたときは、推測で修正させずデータベースやレスポンスを直接確認してから原因を特定した

AIを使うと**コードが冗長になりやすく、1つの変更でも差分が読みにくくなります**。レビューはメンターにお願いする体制だったため、**1つの機能ごとにPull Requestを細かく分け、1回あたりのレビューの負担を抑える**ようにしました。説明にも「なぜそうしたか」と「相談したい点」を必ず書き、コードだけを追わなくても判断の背景が分かるようにしています。

**AIが書いたコードに不具合が混ざることは前提**として進めました。実際、後述する「既存データを空で上書きしてしまう問題」はレビュー工程で出荷前に見つけたものです。生成されたものをそのまま通さず、**必ず自分の目で確認してから提出する**ことを徹底しました。

## 見つけて直した不具合

### 保管庫の編集画面で、既存データを空で上書きしてしまう問題

パスワード管理の編集画面で読み込みに失敗した場合、空のフォームが表示される作りになっていました。利用者がそこに入力し直して保存すると、**サーバー上の既存データが空の内容で上書きされます**。読み込みに失敗したときはフォーム自体を表示しないよう修正しました。

### 申請を承認してもイベントが作られない問題

「承認しても何も起きない」という報告を受け、推測せずにデータベースを直接確認しました。**承認済みの申請があるのに、対応するイベントもアーティストも存在しない**ことが分かり、承認処理が状態を書き換えるだけだったのが原因と特定。承認時にイベント(必要ならアーティストも)を作成するよう変更しました。

その際、二人が同時に承認するとイベントが二重に作られる可能性があったため、トランザクション内で「まだ承認されていないこと」を条件に状態を確定させています。

### 画像が表示されない問題の切り分け

投稿した画像が表示されない不具合について、保存されている URL に直接アクセスして `400 Bucket not found` を確認し、**コードではなくストレージのバケットが非公開設定だったこと**を原因として特定しました。

## チーム開発で意識したこと

- **担当を画面単位で縦割りにする**ことで、同じファイルを複数人が同時に触る状況を避けた
- **他の人の担当ファイルは、必要になっても勝手に変更せず、先に共有してから触る**ようにした。共通ファイル(API ラッパーなど)の変更も同様
- Pull Request のレビューはメンターにお願いする体制だったため、**1機能ごとに小さく分けて出す**ようにした(理由は前章)
- 他のメンバーの PR がマージされて自分の PR が衝突した場合は、**自分の PR 側を rebase して解消**し、相手のブランチには手を出さなかった

## 振り返り

3日間という制約の中で、**作らない判断**が成果に直結することを実感しました。投稿への返信機能を付けなかったこと、状態管理ライブラリを入れなかったことはいずれもその例です。

また、AIを使うと実装の速度は上がる一方で、**確認の質がそのまま成果物の質になる**ことがはっきりしました。生成されたコードは動いて見えても、読み込み失敗時のような例外的な経路に問題が残ります。ここを見つけられるかどうかが、AIを使う開発での自分の価値だと考えています。

統合してから見つかる不具合(画像が表示されない、承認しても何も起きない)は、個々の実装ではなく**画面をまたいだ動作確認でしか見つからない**ものでした。次に同じ規模の開発をするなら、機能単位の実装と並行して、通しで触る時間を早い段階から確保します。
